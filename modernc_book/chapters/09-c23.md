# 9. The C23 Language

C23 is the 2024 revision of the ISO C standard, commonly called C23. It modernizes familiar C without turning it into C++. Its features are best adopted where they improve clarity or correctness; portable projects must still verify compiler and standard-library implementation support.

## 9.1 Booleans and null pointers

```c
bool valid = true;
int *ptr = nullptr;
if (!valid || ptr == nullptr) {
    /* handle absence */
}
```

`bool`, `true`, and `false` are language keywords in C23. `nullptr` has type `nullptr_t` and denotes a null pointer constant without relying on a macro such as `NULL`.

## 9.2 Type inference with auto and typeof

```c
int count = 3;
auto copy = count;            /* copy has type int */
typeof(count) another = 4;   /* another has type int */
```

The C23 `auto` form is a type inference declaration, not the C++ rules in their entirety. `typeof` provides a type based on another expression or type name. C23 also supplies `typeof_unqual`, discarding qualifiers and atomicity from the resulting type in its specified way. These mechanisms can reduce duplicated types but should not obscure API contracts.

## 9.3 Constant expressions

```c
constexpr int channels = 4;
int measurements[channels];
```

C23 introduces `constexpr` for certain objects initialized by constant expressions. This is not C++ compile-time function evaluation. Keep the distinction between an expression computable at translation time and a runtime `const` object.

## 9.4 Width-aware integers

Where supported, `_BitInt(N)` and `unsigned _BitInt(N)` provide bit-precise integer types. Their availability and limits depend on implementation support. They can be valuable for numerical kernels and hardware-oriented code, but ordinary public interfaces may prefer portable fixed-width types when widths are already covered by `<stdint.h>`.

## 9.5 Binary literals and digit separators

```c
unsigned mask = 0b1010'0101;
```

Binary literals communicate bit patterns; the single-quote separators make long constants easier to read. A leading `0b` is now standardized rather than a vendor extension.

## 9.6 Attributes

```c
[[nodiscard]] int save_record(void);
[[maybe_unused]] static int debug_setting = 0;
```

Standard attribute syntax provides optional diagnostics and intent. `[[nodiscard]]` encourages checking a result; the exact diagnostic is implementation-dependent. Attributes do not magically enforce a full error-handling policy. C23 also specifies `[[deprecated]]`, `[[fallthrough]]`, and `[[noreturn]]` as well as forms of `[[unsequenced]]` and `[[reproducible]]`.

## 9.7 New preprocessor capabilities

C23 adds `#embed` for incorporating binary data at translation time and `#warning` for diagnostics. `__VA_OPT__` permits more reliable conditional comma handling in variadic macros. Implementation support for `#embed`, in particular, requires explicit checking.

## 9.8 Checked arithmetic and bit utilities

C23 specifies `<stdckdint.h>` with `ckd_add`, `ckd_sub`, and `ckd_mul` for checked integer arithmetic, and `<stdbit.h>` for unsigned integer bit operations. These facilities may be missing in otherwise C23-capable runtime libraries. A project that depends on them should run configure-time feature tests. Do not assume a working `-std=c23` flag implies complete header support.

## 9.9 A migration policy

First build with maximum practical warnings. Remove implicit declarations and invalid conversions; make allocation-size checks explicit; audit dangerous signed arithmetic; identify any reliance on extensions. Introduce `nullptr`, boolean keywords, binary literals, designated/empty initializers, and attributes only when supported by the actual deployment toolchains. A robust migration preserves behavior before improving style.

## 9.10 Generic selection

C's `_Generic` chooses an expression based on a controlling expression's type. It supports type-directed interfaces while remaining a compile-time selection mechanism. Generic selection is not dynamic dispatch.

```c
#define magnitude(x) _Generic((x), \
    float: fabsf, \
    double: fabs, \
    long double: fabsl \
)(x)
```

This example requires `<math.h>`. It illustrates a common pattern: select an appropriately typed function, then call it. The supported type list is intentionally explicit; passing an unsupported type is a constraint violation unless a `default` association is provided. `_Generic` predates C23, but remains important when designing a modern C interface.

## 9.11 Safer use of `typeof`

When an expression's type is cumbersome, `typeof` can keep an interface aligned with the expression itself. It does **not** turn C into a language with automatic lifetime management. A pointer inferred from another pointer has the same potential lifetime hazards.

Use inferred types when duplication creates maintenance risk, but write explicit types when they communicate important width, ownership, or protocol constraints.

## 9.12 Checked arithmetic in C23

When available, `<stdckdint.h>` supports checked integer calculations that report overflow through a boolean result rather than leaving the programmer to reconstruct each type's boundary conditions.

```c
#include <stdckdint.h>
int result;
if (ckd_add(&result, a, b)) {
    /* the mathematical result is not representable in result's type */
} else {
    /* result contains the sum */
}
```

The above is a C23-library-dependent fragment, not a guarantee that every compiler installing a C23 front end also ships this header. For targets without it, a tested manual check or compiler-specific checked-arithmetic primitive may be appropriate.

## 9.13 Selected portability cautions

Not all useful C23 additions are equivalent from a portability standpoint. Binary literals and attributes may be available before other features. `#embed` support can vary independently from the core language. Bit-precise integers may have target-specific maximum widths. Headers such as `<stdbit.h>` may be absent from older C libraries.

Keep a portability table stating which implementation combinations were actually tested. The standard defines what a conforming implementation must do; deployment engineering determines which implementation is in hand.

## 9.15 What actually changes when moving from C17

C23 is not merely a new spelling of old constructs. It removes traditional, unprototyped function declarations and old-style function definitions. In C23, `void work()` declares a function taking no arguments; older C dialects treated an empty parameter list differently outside a function definition. This is especially important in legacy headers.

C23 also fixes signed integer representation to two's complement. It does **not** define signed overflow. The two statements are compatible: an implementation has a required representation, while the result of evaluating an overflowing signed arithmetic expression remains undefined.

The macro `__STDC_VERSION__` is defined as `202311L` in C23 mode for conforming implementations. Checking this can select a language-level path, but it cannot certify that a particular runtime library or optional capability is present.

## 9.16 The boundary between auto and typeof

C23 introduces type inference for declarations with `auto` and standardizes `typeof` and `typeof_unqual`. These facilities eliminate some redundant type spellings. They do not provide templates, classes, overload resolution, or C++-style deduction rules.

A library's public signature should normally state the types important to its binary contract: `uint32_t`, `size_t`, or a named structure. Locally, inferred types can be useful where the type is unambiguous from the initializer and repeating it would be error-prone.

C23 `constexpr` applies to certain constant objects under specific restrictions; it is not general C++ constant evaluation. For example, C23 does not make an arbitrary user-written function eligible for execution during translation merely because it is called from a constant initializer. A `constexpr` object should not be used to promise behavior that the actual compiler has not implemented.

## 9.17 Modernized enumerations and attributes

C23 adds facilities for enumerations with explicitly selected underlying integer types. They can make intent clear when enum values appear in compact data structures or interfaces. Still, an enum object in a wire format must be serialized as an explicitly chosen integer representation; the in-memory layout should not be transmitted wholesale.

Attributes such as `[[nodiscard]]` help advertise contracts. They improve diagnostics but are not enforcement mechanisms: a caller may still discard a return value and a conforming implementation's diagnostic behavior depends on the attribute rules. Code review and tests remain necessary.

## 9.18 Checked arithmetic belongs at boundaries

When the implementation supplies `<stdckdint.h>`, `ckd_add`, `ckd_sub`, and `ckd_mul` can help test whether the mathematical result is representable in the result type. Use them when dealing with byte counts, sizes and input-derived values. Do not confuse this check with validating the semantic limits of a protocol. A packet length may fit in a `size_t` while still exceeding the application's maximum frame length.

Some deployments provide a C23 compiler without the corresponding C23 library headers. The right adaptation is a feature check at configuration time, or a small, tested fallback module with exactly the same contract. A bare compiler-version comparison is less reliable than verifying the required operation.

## 9.19 C23 migration example

Suppose a legacy API relied on `malloc(count * width)`. Migrating to C23 is a chance to fix the arithmetic contract before introducing new syntax:

```c
#include <stdint.h>
#include <stddef.h>
#include <stdlib.h>
#include <stdbool.h>

bool allocate_bytes(size_t count, size_t width, void **out)
{
    if (out == nullptr || count == 0 || width == 0 ||
        count > SIZE_MAX / width)
        return false;
    void *memory = malloc(count * width);
    if (memory == nullptr)
        return false;
    *out = memory;
    return true;
}
```

The routine refuses zero-sized requests and leaves the output unchanged on failure. It does not assert that all targets offer a usable heap. In freestanding firmware, a caller-provided arena may be preferable.

## 9.20 A testable feature inventory

Record support separately for language syntax, library headers, implementation-defined properties, and target environment. The first category includes `nullptr`, `typeof`, and `constexpr`. The second includes `<stdckdint.h>` and `<stdbit.h>`. The third includes integer widths and alignment. The fourth includes available heap, streams, threads, and atomics.

## 9.21 A concrete subset of C23

The following complete program deliberately selects language features that are supported by the book's intended GCC 14 and Clang 18 test matrix. It does not exercise the newer library headers or `#embed`, which must be checked independently.

```c
#include <stdio.h>

struct point { int x, y; };

int main(void)
{
    auto flags = 0b1010'0101u;
    typeof(flags) another = 0b0000'0011u;
    struct point origin = {};
    int *missing = nullptr;
    bool good = (flags & another) == 1u;

    static_assert(sizeof(flags) == sizeof(unsigned));
    if (!good || origin.x != 0 || origin.y != 0 ||
        missing != nullptr)
        return 1;
    puts("C23 essentials: OK");
}
```

The integer literal is explicitly unsigned. The digit separator is a single quote between digits. The `auto` declaration infers the type from its initializer, and `typeof(flags)` names that type again. Empty initialization initializes both structure members to zero. `nullptr` provides a null pointer constant. The `static_assert` condition is evaluated at translation time.

The repository keeps a corresponding standalone program in `examples/c23_basics.c`. When teaching this listing, compare what the compiler knows at translation time with what the program checks at runtime.

## 9.22 Why not use every C23 feature in the first example?

A language revision consists of many individually specified changes. A compiler may support the new keywords but lack the new embedding directive. Its system C library may lack `<stdckdint.h>` or `<stdbit.h>`. A microcontroller toolchain may implement only a subset of hosted interfaces.

Choosing a well-supported subset for the introductory example makes the core lesson reproducible. Dedicated feature probes are the right place to demonstrate `constexpr`, bit-precise integers, the newer enumeration facilities, and the new library interfaces across toolchains.

## 9.23 Initialization is not byte filling

`struct point origin = {};` uses language-level initialization, not a raw `memset`. C's initialization rules set members to their appropriate empty-initialization values. This distinction matters for structures containing pointers or floating members, because an all-bits-zero representation is not universally promised to be the semantic null-pointer or floating zero representation.

For an ordinary aggregate, correct language initialization is usually both clearer and more portable than relying on representation bytes.

## 9.24 A language revision is a collection of independent features

Using `-std=c23` selects a language mode, but the compiler and standard library are not always delivered or updated together. A cross-compiler may recognize `nullptr` and `typeof` while its libc lacks `<stdckdint.h>`. The correct deployment procedure tests the exact construct or library interface that the project uses.

Classify features before adopting them. Some are purely syntactic improvements, such as binary literals and more convenient forms of initialization. Some change type expressiveness, such as bit-precise integers. Others require new translation support, such as `#embed`. Still others require implementation of additional library headers.

That taxonomy prevents a migration effort from becoming a blind replacement of every old idiom with a new-looking construct.

## 9.25 C23 integer literals and readable masks

Binary literals represent bit patterns compactly:

```c
unsigned control = 0b1010'0001u;
```

The single quotes separate digit groups without affecting value. This is useful when a device control register is documented by bit positions. It does not solve the hardware semantics: whether a register is read-only, write-one-to-clear, or requires reserved bits depends on the device manual.

Clang 18 in some configurations diagnoses the standardized C23 binary-literal syntax with a GNU-extension warning. Our CI retains `-Werror` but suppresses that one diagnostic for Clang 18. A warning emitted by a compiler version is not necessarily evidence that the source violates the language standard.

## 9.26 nullptr is a value, not an owner

C23's `nullptr` is a null pointer constant with type `nullptr_t`. It makes pointer intent clearer than writing integer zero in a pointer context. But replacing `NULL` with `nullptr` does nothing to prevent a non-null dangling pointer, a wrongly sized array, or a double free.

The following check rejects absence, not invalid lifetime:

```c
if (buffer == nullptr)
    return false;
```

A buffer that was freed but whose old pointer has not been reset may still compare non-null. The API must prevent access after the owner's release, not hope that an address test will discover it.

## 9.27 Type inference should not hide the contract

C23's `auto` can infer a local type from its initializer. This can avoid spelling a complex expression type twice, and `typeof` can express a related declaration. However, the public interface of a protocol decoder should not hide that its input is `const unsigned char *` with a `size_t` length or that a field is a fixed-width integer.

At public boundaries, explicit types communicate ABI and range requirements. Inside a function, type inference is helpful when the initializer makes the meaning obvious. Use it as a maintenance aid, not a substitute for reviewing conversions.

## 9.28 Checked integer arithmetic in a C23 library

The `ckd_add`, `ckd_sub`, and `ckd_mul` interfaces from `<stdckdint.h>` express checked operations with a result pointer. They are especially useful for sizes and accumulated counts.

A feature probe should include the header, call a chosen macro with values that fit and values that overflow, and link the resulting program using the actual target C library. If the header is missing, a separately tested implementation of equivalent arithmetic checks may be reasonable. A compiler version alone is insufficient evidence.

The application may need a limit stricter than the type's representable range. A frame size of 65,000 bytes can be representable in `size_t` yet impossible to buffer in a 2 KB MCU arena. Checked arithmetic and application resource checks solve different problems.

## 9.29 Choosing what to modernize

A conservative migration can proceed in three phases. First, make the old program correct under its current contracts: fix implicit assumptions, mismatched prototypes, unchecked sizes and invalid conversions. Next, select the C23 language mode and confirm equivalent behavior under tests. Finally, adopt newer features where they improve readability or reliability.

Do not rewrite a working fixed-size state machine solely to exhibit `_BitInt` or `typeof`. A textbook should show what the feature contributes and what its portability cost is. For firmware, support across required cross-toolchains is often more important than showcasing every new keyword.

## 9.30 One standard, several implementation layers

C23 is the language revision published as ISO/IEC 9899:2024. The same phrase 'supports C23' can describe very different states of implementation. A compiler front end may accept new syntax while the selected C library is missing a corresponding header. A hosted implementation may offer features unavailable in a freestanding MCU runtime. A particular back end may support a bit-precise type only up to a limited width.

For a reliable project, record support in separate columns:

| Question | Example of evidence |
| --- | --- |
| Does the language front end recognize the feature? | Compile a minimal translation unit in C23 mode |
| Does the required library facility exist? | Include the header, use its operation, then link |
| Does the target support its representation? | Build and execute target-specific range and size tests |
| Is the feature permitted in the deployment context? | Review the implementation and RTOS/ISR documentation |

The macro `__STDC_VERSION__` has the value `202311L` in a conforming C23 translation mode. It communicates the claimed language revision; it is not a substitute for the additional checks above.

The GCC and Clang projects publish changing C-standard support matrices. Use those project pages as starting points, then verify the exact compiler, library, target and feature in the release being deployed.

## 9.31 constexpr is an object feature, not C++ constexpr functions

C23 introduces `constexpr` for certain objects with constant initializers. It does not provide C++'s general facility for executing arbitrary user-written functions during translation.

An illustrative C23 declaration is:

```c
constexpr int samples_per_frame = 160;
static_assert(samples_per_frame > 0);
```

The initializer must meet the feature's translation-time requirements, and the object cannot be modified afterward. C23 `constexpr` has restrictions, including exclusions for atomic and volatile objects and for most non-null pointer values.

Do not assume that every compiler supporting `-std=c23` implements `constexpr` objects in the selected release. Compile this minimal example separately before relying on it. If a firmware target uses an older compiler, an enumeration constant or a suitably scoped macro may meet an application requirement without forcing a toolchain migration.

## 9.32 Bit-precise integers have specific ranges

The `_BitInt(N)` family makes it possible to request an integer type with a chosen value width, within an implementation-supported range. For a signed nine-bit value, the mathematical range is −256 through 255. An unsigned nine-bit value can represent 0 through 511.

```c
_BitInt(9) signed_sample = -200;
unsigned _BitInt(9) channel_code = 500;
```

These types are especially interesting for tightly specified bit-oriented computations and representations. Yet a bit-precise C type does not, by itself, dictate a portable nine-bit wire format or guarantee compact storage without padding on every target. External packets still need explicit packing and extraction.

Implementation limits, type promotions, ABI conventions and library-format support deserve attention. Do not pass an arbitrary bit-precise value to `printf` using a format intended for `int` without first establishing a safe conversion and format contract.

## 9.33 Checked arithmetic from the C23 library

The header `<stdckdint.h>` provides `ckd_add`, `ckd_sub`, and `ckd_mul`. They test whether an integer calculation is representable in the destination type and report an overflow condition.

A compile-and-run feature probe can be written as a standalone file:

```c
#include <limits.h>
#include <stdckdint.h>

int main(void)
{
    int result = 0;
    if (ckd_add(&result, 10, 20) || result != 30)
        return 1;
    if (!ckd_add(&result, INT_MAX, 1))
        return 2;
    return 0;
}
```

A nonzero result or failure to compile or link means the application cannot rely on this facility as tested. On overflow, do not assume the result object preserves an earlier value; if your API promises unchanged output on failure, compute into a temporary and assign only after the checked operation succeeds.

A more restrictive application limit remains independent. A count can fit in `size_t` but exceed the capacity of an arena, message queue, or peripheral packet buffer.

## 9.34 Bit utilities are not rotate operators

C23's `<stdbit.h>` provides operations for tasks such as counting set bits, counting leading or trailing zeros, querying bit width, and computing bit-floor or bit-ceil values. It does not provide a C interface named `std::rotl` or `std::rotr`, which belong to C++.

If an implementation provides the new header, a small feature probe that calls `stdc_count_ones` on an unsigned integer can establish the facility needed by an application. The portable rotation functions in Chapter 14 use ordinary unsigned shifts and explicitly avoid shifting by the type width.

Do not assume the binary representation of a C object equals the byte order of a file or external wire format. Bit operations compute on integer values; serialization independently defines where each octet goes.

## 9.35 Embedding a resource into a program

C23's `#embed` directive is designed to incorporate the bytes of a resource at translation time. A possible use is storing a small static lookup table or model constant inside firmware:

```c
static const unsigned char resource[] = {
#embed "coefficients.bin"
};
```

This is a feature illustration, not a guaranteed portable build for every compiler used by this book. A real build must supply the resource file, arrange an appropriate search path, test the compiler's support, and validate the embedded format and length.

It also must consider the target linker script and memory placement. The C source alone does not promise that a large resource will reside in flash rather than consuming precious RAM. A generated C array may provide a fallback on an older toolchain.

Embedding bytes also does not authenticate the resource. The build pipeline must establish where the file came from and whether its contents match the expected model or calibration data.

## 9.36 Attributes assist review but do not replace contracts

C23 attribute syntax can communicate useful information to tools. For example, `[[nodiscard]]` can document that a result should not normally be discarded. That may produce a compiler warning if the caller ignores the result, but it does not make incorrect error handling impossible.

A declaration such as

```c
[[nodiscard]] bool write_record(const unsigned char *data,
                                size_t length);
```

still needs a contract: which lengths are valid, when null is permitted, what failure means, and whether any bytes might have been written before returning false. Attributes improve communication; they do not settle resource ownership or partial side effects.

## 9.37 Treat migration as a tested engineering change

For legacy source, first correct implicit assumptions: unprototyped declarations, unsafe conversions, unvalidated sizes, and ownership confusion. Build and run the old program in its supported mode, recording results. Next select C23 mode and repair genuine standard incompatibilities. Finally adopt new features where they clarify a design and are supported by required toolchains.

Changing language mode and rewriting every algorithm in the same commit makes regressions difficult to attribute. A staged migration retains meaningful test evidence.

The book's CI deliberately uses a conservative tested feature subset for standalone examples. More advanced features such as `constexpr`, `_BitInt`, and `#embed` should receive their own compatibility probes before being made dependencies of the full build.
