# 6. Input, Output, and Files

C's hosted I/O library is built around streams. A stream may refer to a terminal, ordinary file, or implementation-specific source. Errors should be treated as part of the computation.

## 6.1 Reading lines safely

```c
#include <stdio.h>
#include <string.h>

int main(void)
{
    char line[256];
    while (fgets(line, sizeof line, stdin) != nullptr) {
        size_t n = strlen(line);
        bool complete = n > 0 && line[n - 1] == '\n';
        printf("bytes=%zu complete=%s\n", n, complete ? "yes" : "no");
    }
    if (ferror(stdin)) {
        fputs("input error\n", stderr);
        return 1;
    }
}
```

A full buffer does not imply a complete line. The next `fgets` may read the rest. Embedded applications frequently need a bounded protocol parser rather than a line-oriented parser.

## 6.2 Formatted I/O

`printf` uses a format string to interpret subsequent arguments. A mismatch between conversion specifications and argument types can yield undefined behavior. Never use untrusted input as the format string:

```c
printf("%s", user_text); /* fixed format */
```

For integers of exact width, use `<inttypes.h>` formatting macros. For `size_t`, use `%zu`. Avoid relying on the fact that two types happen to share a representation on one platform.

## 6.3 Binary I/O

```c
unsigned char buffer[1024];
size_t got = fread(buffer, 1, sizeof buffer, stdin);
if (got < sizeof buffer && ferror(stdin)) {
    fputs("read failure\n", stderr);
}
```

A binary protocol needs a documented byte order, field widths, bounds, and error policy. Reading bytes into a native structure is not sufficient. The portable approach decodes fields explicitly.

## 6.4 Files and cleanup

```c
FILE *fp = fopen("output.txt", "w");
if (fp == nullptr) {
    perror("output.txt");
    return 1;
}
if (fputs("record\n", fp) == EOF || fclose(fp) == EOF)
    return 1;
```

The short example needs care: if `fputs` fails, short-circuit evaluation skips `fclose`, leaking the open stream. Real cleanup logic must close the file on every path, then report either the write error or the close error. A successful write call does not guarantee that data is durably stored.

## 6.5 The difference between text and bytes

A text stream may transform representations, notably line endings on some systems. Binary I/O is suited to exact bytes. If a file is a protocol packet or serialized image, open it with `"rb"` or `"wb"` in hosted implementations and define the byte format explicitly.

A read of `n` bytes is not guaranteed to deliver `n` bytes in one call. A short `fread` result must be interpreted using `feof` and `ferror`, and the caller must decide whether a short record is valid or malformed.

## 6.6 A bounded line counter

Some tasks need only one pass over input and almost no memory:

```c
#include <stdio.h>
#include <stdbool.h>
#include <limits.h>

bool count_newlines(FILE *stream, unsigned long *result)
{
    if (stream == nullptr || result == nullptr)
        return false;

    unsigned long count = 0;
    int ch;
    while ((ch = fgetc(stream)) != EOF) {
        if (ch == '\n') {
            if (count == ULONG_MAX)
                return false;
            ++count;
        }
    }
    if (ferror(stream))
        return false;
    *result = count;
    return true;
}
```

The function counts newline characters, which may differ from a human notion of lines if the final input has no trailing newline. Documenting that distinction matters more than choosing one rule universally. The caller owns the stream, so this function neither opens nor closes it.

## 6.7 Reading numeric text

Using `scanf` indiscriminately can make validation difficult: conversion success, partial input, range errors, and leftover text all matter. For untrusted input, reading a bounded line and then using `strtol` or another checked parser often exposes the contract more clearly.

A parser should specify whether whitespace is accepted, whether leading `+` or `-` is legal, whether trailing characters are rejected, and the range of accepted values. A caller should not infer all of those policies from the function name alone.

## 6.8 File cleanup paths

A file-writing function commonly needs two independent success checks: whether the write succeeded, and whether closing the stream succeeded. Avoid short-circuiting away the close operation:

```c
bool ok = fputs("record\n", fp) != EOF;
if (fclose(fp) == EOF)
    ok = false;
```

This makes the cleanup action unconditional once the stream has been opened successfully. It does not guarantee that written data is durable after a power loss, since operating systems and storage devices may buffer writes.

## 6.10 A byte-stream copier

Reading and writing streams is not a single operation when short transfers are possible. A robust file copier reads a bounded block, then writes every byte obtained or reports an error. The `fwrite` interface returns the number of complete elements written; when the element size is one byte, that count can be compared directly with the requested byte count.

The repository's `examples/file_copy.c` illustrates this pattern for standard input and output. It checks `ferror(stdin)` when a short read occurs and `fflush(stdout)` before returning success. It still does not guarantee durability against an operating-system crash or power loss. That stronger guarantee is outside the portable C stream contract and may require platform-specific synchronization.

A binary copier preserves byte values; a text-processing program may interpret newline conventions, encodings, and locale. The distinction should be part of the program's specification.

## 6.11 Why parsing after input is often easier

An unchecked numeric scan mixes syntax recognition with conversion. It can be difficult to determine whether a trailing character remains or a number was only partially consumed. Separating operations makes behavior explicit: read a bounded line; determine whether the entire line matches the required grammar; then perform checked numeric conversion.

For example, a temperature configuration file might permit optional leading whitespace but forbid any trailing nonspace characters. That is a different grammar from a telemetry message consisting of exactly four decimal digits. Neither grammar is universally correct. A well-designed parser names and tests the distinction.

Use `strtol` or `strtoul` when their grammar matches the intended input. Set `errno` to zero before the call, use the end pointer to detect whether any digits were converted and whether unconsumed input remains, and inspect `ERANGE`. Then check that the result fits the application type. A successful library conversion is not proof that all application constraints were met.

## 6.12 Error reporting preserves the cause

A function returning only zero or one may be sufficient for a toy program. In a larger system, distinguish an open failure, a read error, malformed content, a short write, and a close failure. These conditions have different remedies and should be logged or propagated without losing their meaning.

If a write fails and closing the file also fails, what should the caller see? One design returns the primary failure and logs cleanup failures separately. Another uses a structured result containing both statuses. The choice should be deliberate. Simply overwriting the first error with the last operation's result can hide the original problem.

## 6.13 Buffering and interleaving

Stream output may be buffered. `fflush` requests transmission of the C library's buffered output to the host environment, not permanent storage. Mixing multiple threads' writes or mixing `stdio` with lower-level operating-system file descriptors can introduce ordering and buffering issues. Portable code should synchronize concurrent stream operations appropriately and should not assume that a line-oriented message is always an indivisible transaction.

## 6.14 Designing a testable input function

Instead of making a parser call `getchar` itself, define a function accepting `const unsigned char *input` and a `size_t` length. Then a small adapter reads from a stream and passes counted buffers to the parser. Host tests can exercise empty input, malformed records, and boundaries without inventing a terminal or fake file.

## 6.15 Streams, records, and short transfers

The C stream library exposes a sequence of bytes or characters; it does not magically preserve an application's record boundaries. Reading 100 bytes from a binary file says nothing about where one protocol record ends. If the format has a length field, the parser must validate that field and obtain exactly the corresponding number of bytes or explicitly report incomplete input.

A complete fixed-size record reader may loop until it has accumulated the required count, encounters an error, or reaches clean EOF before the record is complete. These outcomes are different. In particular, clean EOF between records is normal, whereas EOF in the middle of a required record often indicates truncation.

For an interactive terminal, line processing introduces other questions. What counts as end-of-line on this host? Is the input a text stream or a binary stream? How should excessively long lines be rejected or drained? Do not use \`fgets\` as if it guaranteed one whole logical line when its buffer is finite.

## 6.16 Write operations have partial-success semantics

A \`fwrite\` call returns the number of complete elements written, and a short result signals failure under its contract. For arbitrary byte counts, choose an element size of one and compare the returned count with the requested bytes. In a broader abstraction over operating-system calls, writes may also return a positive short count and require a loop to finish the request. Do not conflate the contracts of different APIs.

A robust writer distinguishes the amount of data accepted, the error status, and whether retry is meaningful. On nonblocking devices, a temporary inability to write should not necessarily be treated as fatal. Conversely, looping forever on a zero-byte result would violate bounded-progress expectations.

When writing a file, checking \`fclose\` remains important because some errors can surface after prior buffered operations appeared successful. Even a successful close does not universally mean data is physically durable after sudden power loss.

## 6.17 Use a parser independent of the transport

A reusable packet decoder can accept a pointer, length, and output destination:

\`\`\`c
bool decode_packet(const unsigned char *bytes,
                   size_t length,
                   struct packet *out);
\`\`\`

The parser does not call \`getchar\`, open a file, or read a UART register. Instead, adapters gather bytes from those sources and call the same decoder. A desktop test can supply a deliberately truncated packet, an invalid length, or a checksum mismatch without requiring hardware. Device-level tests can then focus on acquisition and timing.

There is a cost: the adapter must buffer enough bytes for a record, or the parser must be designed as a streaming state machine. The right choice depends on maximum frame size and available RAM.

## 6.18 Standard output and error output

\`stdout\` and \`stderr\` serve different roles. Machine-readable output should be written to \`stdout\`, while explanatory error messages usually belong on \`stderr\`. A program that produces a table can then be piped into another tool without contaminating its data with diagnostics.

For command-line tools, establish an exit-status convention: zero for success and nonzero for failure. If there are many error categories, the exact exit values may be less informative than a precise error message, but the contract should still be predictable.

An embedded firmware component may not have any of these streams. It may instead return a structured status to its caller or emit a diagnostic over a separately configured telemetry channel. The error model survives even when the transport differs.

## 6.19 A defensive byte-count example

Suppose a header says the payload is \`length\` bytes, and the caller has a \`capacity\`-byte buffer. Reject an oversized payload before copying. If the total frame needs five extra octets, check \`capacity >= 5\` and then \`length <= capacity - 5\`. A direct test of \`length + 5 <= capacity\` can overflow unsigned arithmetic before the comparison.

This tiny transformation is a recurring pattern in systems programming: convert a potentially overflowing sum into a subtraction after establishing its precondition.
